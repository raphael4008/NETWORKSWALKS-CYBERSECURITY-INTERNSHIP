1. Executive Summary

This report documents a structured security assessment of medirozahospital.com, a NetworkWalks Academy Vulnerability Assessment & Penetration Testing (VAPT) laboratory target (Batch B082). The engagement followed a PTES-aligned methodology across six phases and evaluated public-facing infrastructure, DNS footprint, exposed web content, transport-layer security, and the authentication surface.

The reconnaissance and enumeration phases were completed successfully. The target resolves to 199.188.201.16 (server274-1.web-hosting.com, United States) on Namecheap shared hosting. A LiteSpeed web server sits behind an active LiteSpeed Web Application Firewall (WAF). The cryptographic posture is modern (TLS 1.2/1.3 only, strong ciphers, valid SSL.com certificate), but the application layer exposes several weaknesses: directory indexing on sensitive paths, exposed administrative and webmail interfaces, and a complete absence of defensive HTTP security headers.

Status of the active phases. Reconnaissance, enumeration and vulnerability analysis are complete. During the Gaining Access phase the initial credential attempt produced false positives (a misconfigured failure string), and the target's WAF temporarily escalated to a site-wide JavaScript challenge. Once the browser session cleared the challenge, manual analysis uncovered the most significant weakness of the engagement: an exposed database backup containing staff and shareholder PII (names, emails, phone numbers, national ID numbers and salaries), together with live directory indexing and a username-enumeration flaw that confirmed admin as a valid account. A corrected credential test still did not recover the password. Consequently, Exploitation and Post-Exploitation were not reached. This report documents the full analysis, the root causes, and the corrective path forward.

7. Phase 3 — Vulnerability Analysis (Findings)

Finding 1 — Exposed Sensitive Directories & Directory Indexing

  • Severity: High · CWE: CWE-548 (Information Exposure Through Directory Listing)
  • Details: robots.txt discloses /patient/, /staff/ and /old/; Nikto confirmed directory indexing is active on all three.
  • Impact: Unauthenticated browsing of internal file trees, potentially revealing medical records, staff data, and legacy assets.

Finding 2 — Exposed Administrative & Mail Interfaces

  • Severity: Medium · CWE: CWE-552
  • Details: /cpanel/ and /securecontrolpanel/ (hosting control panels), /webmail/ (IlohaMail 0.8.10 — known XSS), /mailman/listinfo (GNU Mailman).
  • Impact: Expanded attack surface for credential brute-forcing and software-specific exploitation.

Finding 3 — Missing HTTP Security Headers

  • Severity: Low–Medium · CWE: CWE-693
  • Details: Missing Strict-Transport-Security, Content-Security-Policy, X-Content-Type-Options, Referrer-Policy, and Permissions-Policy.
  • Impact: Increased exposure to clickjacking, MIME-sniffing, protocol downgrade, and content-injection attacks.

Finding 4 — Public Sitemap & Endpoint Enumeration

  • Severity: Informational
  • Details: /sitemap.xml enumerates /index.html, /about.html, /doctors.html, /contact.html.
  • Impact: Facilitates targeted content discovery (reconnaissance aid).

Finding 5 — Weak Email Authentication Policy

  • Severity: Low
  • Details: DMARC record set to p=none; SPF ends in ~all (soft fail).
  • Impact: Reduced protection against email spoofing and phishing.

Finding 6 — Automated-Scanner Blocking & Anti-Bot Escalation

  • Severity: Informational
  • Details: LiteSpeed WAF returns 403 to standard scanners and temporarily served a site-wide JavaScript browser-verification challenge after heavy automated traffic. This is a defensive strength, but it constrains automated testing and requires browser-driven methods.

Finding 7 — Exposed Database Backup Containing Sensitive PII

  • Severity: Critical · CWE: CWE-538 (File/Directory Information Exposure), CWE-200
  • Details: /old/mediroza_db_backup_2019.sql (≈6.3 KB) is downloadable without authentication. It contains the staff and shareholders tables with names, roles, departments, corporate email addresses, phone numbers, national ID numbers, salaries and hire dates.
  • Impact: Serious data-protection/regulatory exposure and a ready-made target list for social engineering and phishing.

Finding 8 — Username Enumeration on Authentication Endpoints

  • Severity: Medium · CWE: CWE-204 (Observable Response Discrepancy)
  • Details: /patient/login.php and /staff/login.php return Username not found for a non-existent account versus Incorrect password for a valid one. This confirmed admin as a valid account.
  • Impact: Enables reliable account discovery, accelerating credential attacks.

Finding 9 — Live Directory Indexing Exposing Application Files

  • Severity: High · CWE: CWE-548
  • Details: /old/, /patient/ and /staff/ render file listings. /patient/ exposes reports/, download.php, error_log (251 KB), portal.php and logout.php; /staff/ exposes login.php.
  • Impact: Maps the internal application structure and reveals a downloadable database backup (Finding 7).

Finding 10 — Technology & Version Disclosure

  • Severity: Low · CWE: CWE-200
  • Details: X-Powered-By: PHP/8.2.36 header and <meta name="generator" content="Mediroza CMS 1.4.2">.
  • Impact: Aids attackers in matching exploits to specific versions.

Finding 11 — Weak Session Cookie Attributes

  • Severity: Low–Medium · CWE: CWE-1004 / CWE-1275
  • Details: Set-Cookie: PHPSESSID=…; path=/; secure — HttpOnly and SameSite are not set.
  • Impact: Session cookies are exposed to client-side script access (XSS) and cross-site request behaviour.

8. Phase 4 — Gaining Access

The first attempt failed because of a false-positive detector combined with a temporary anti-bot escalation. After clearing the challenge with a real browser session, the login endpoint was analysed properly: a valid account (admin) was confirmed through username enumeration, but the password was not recovered.

8.1 Initial blocker — anti-bot challenge and a false positive

Heavy automated traffic triggered a site-wide JavaScript challenge ("Please wait while your request is being verified…"), which automated clients cannot pass. In this state the original credential run reported "16 valid passwords found", which was invalid because (i) -l user.txt sent a filename as the username, (ii) the failure string F=incorrect never appeared in the anti-bot page, so every attempt scored as success, and (iii) no session was ever established.

8.2 Correct procedure and corrected result

With the challenge cleared in a real browser, the true login form was recovered: method="POST" action="login.php", fields username and password, and no CSRF token. Response analysis revealed a username-enumeration flaw (Finding 8): a non-existent user returns Username not found, while a valid user with a wrong password returns Incorrect password. This confirmed admin as a valid account.

# Corrected hydra invocation (valid user + exact failure string):
$ hydra -l admin -P targeted_passwords.txt -t 2 -f -V -s 443 medirozahospital.com \
    https-post-form "/patient/login.php:username=^USER^&password=^PASS^:F=Incorrect password"

A targeted 130-entry list (targeted_passwords.txt) completed with 0 false positives and 0 hits, and a broader 1,050-entry common-password list was likewise exhausted at the rate-limited throughput (≈40 attempts/min) without a match. The method is now correct; the password is simply not a common one.

Conclusion for this phase. The detection logic is fixed and a valid username (admin) is confirmed, but no password was recovered, so no authenticated session was obtained. Brute force is impractical here because of rate limiting, so access should be pursued via the lab-supplied credentials or the exposed data identified in Phase 3.

9. Phase 5 — Exploitation (Not Achieved)

Exploitation was not performed because no valid authenticated session or confirmed exploitable vector was established in Phase 4. The vulnerabilities identified in Phase 3 are documented and rated, but were not weaponized. Any exploitation would in this authorized lab require first resolving the access blocker below.

10. Phase 6 — Post-Exploitation (Not Reached)

Post-exploitation (privilege enumeration, lateral movement, persistence, data-access proof-of-concept) was not reached. It depends entirely on first obtaining a foothold in Phase 4. This section is recorded as not reached for completeness and honest reporting.

Path to unblock (authorized lab only).
  1. Pause automated traffic; request an IP reset/whitelist from the lab provider so the JS challenge clears.
  2. Use a real browser to pass verification, then inspect /patient/login.php (form action, hidden CSRF tokens, cookies, and the true failure response).
  3. Retest manually with lab-supplied or documented default credentials — not a full rockyou brute force.
  4. Re-run content discovery against the correct IP with proper wordlists and low rate; check /old/, /staff/, /patient/, /webmail/.
  5. Only then proceed to post-authentication enumeration and document post-exploitation.

13. Conclusion & Learning Outcomes

The assessment successfully completed reconnaissance, enumeration, and vulnerability analysis, producing a clear picture of the target's attack surface and a prioritized remediation plan. The cryptographic layer is well configured; the principal risks are at the application layer — exposed directories, administrative interfaces, and missing security headers.

The engagement did not achieve access because the WAF/anti-bot control blocked automated interaction and the credential test was misconfigured (a false positive). These are precisely the kinds of real-world obstacles penetration testers must recognize and handle methodically.

Key Learning Outcomes

  • Validate tool output before trusting it. A brute-force "success" is meaningless without a matching failure condition and a real session.
  • Precision matters. A single digit (192 vs 199) invalidated an entire scan and wasted time.
  • WAFs change the game. When automated tooling is blocked, manual, browser-driven testing and throttling become necessary.
  • Documentation is part of the deliverable. Captured evidence, screenshots, and honest status reporting (including what was not achieved) are as important as the findings themselves.
  • Stay within scope. All work remained inside the authorized lab, with credentials redacted and no destructive actions taken.
Final result: Reconnaissance, enumeration, and vulnerability analysis complete; gaining access blocked by WAF/anti-bot and a credential-test false positive; exploitation and post-exploitation not reached. A clear, safe path to unblock is documented in Section 9.
